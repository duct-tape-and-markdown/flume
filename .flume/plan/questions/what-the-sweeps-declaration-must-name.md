# What the sweep's declaration must name

Two forks, both in `.flume/declaration.ts` — outside every phase's fence, so no
entry can carry either. Raised off build notes
THE-SWEEP-PROMPT-POINTS-AT-THE-PAGES-IT-RESTATES (item 3) and
THE-SUITE-WORKER-WARRANT-STATES-ITS-CONDITION (item 2).

## Fork 1 — `posturePages` omits `posture-sweep.md` itself

`posturePages` is declared as `engineering.md` and `engine-boundary.md`
(`.flume/declaration.ts:135`). But `posture-sweep.md` carries *Standing lenses* —
shape standards applied to code, which is exactly what a phrase delta re-arms the
domain for — and *Routing*'s filing bar. A commit that edits a lens therefore arms
nothing, which is the condition that page's own opener exists to prevent: "without
it a newly-ratified phrase governs only code written after it".

Options:

- **(a) add the page to `posturePages`.** One line. Every lens edit then re-arms the
  whole domain — ~108 tracked files, which *The frontier is decidable* itself prices
  at a hundred ticks at one neighborhood per tick.
- **(b) leave it, and say so on the page.** An edited lens does reach every *future*
  neighborhood, since the sweep re-reads the pages each tick; what it does not do is
  re-read neighborhoods a rotation already covered. This is what the tree does today,
  undocumented.
- **(c) split the page** — the lenses onto a declared posture page, the procedure
  (frontier, stamp, routing) staying out.

My read: (b) is defensible and is already the behavior; the gap is that the page
reads as if it binds retroactively when the declaration says it does not. If the
retroactive read is the one you want, (a) is the one-line change and the rotation
cost is the price.

## Fork 2 — root config carries load-bearing warrants no lens reads

The sweep domain is `src/`, `harness/`, `bin/`, `examples/`, `scripts/`
(`.flume/declaration.ts:134`). Root config is in build's fence and outside that
domain: `vitest.config.ts` had a worker warrant reasoning from a premise the ship
lock had retired, and it was a human noticing through the inbox — not a lens — that
filed it. The expired-narration lens already widens to `.flume/chain.ts` and
`.flume/PROTOCOL.md` for exactly this reason.

A measured instance, in a file no phase may write at all: `.flume/declaration.ts:98`
says "About 4.6 GB at the peak on an 11 GB host", while `docs/CHAIN-AUTHORING.md`,
*What a wave costs in memory* (`:2562`) computes "~4.5 GB of 11 GB" from its own
table, for the same declaration on the same host. The table owns the measurement and
the declaration restates arithmetic off it (`engineering.md`, *Derived state is
computed, never restated beside its source*) — re-derive it or drop it to a pointer;
either way it is an operator edit.

Options:

- **(a) widen the sweep domain** to the root config surface build may write
  (`vitest.config.ts`, `tsconfig*.json`, `*.config.*`). Every lens then reads them —
  including the ones that have nothing to say about a config file.
- **(b) widen the expired-narration lens' own domain clause**, which already carries
  two files outside the domain. Narrower: narration only, no whole-rotation arming
  from a config edit.
- **(c) leave root config to the inbox**, as happened here.

My read: (b). The lens that already reaches outside the domain is the one whose
subject this is, and it keeps a one-line config edit from arming a hundred-tick
rotation.

Either fork leaves `.flume/declaration.ts` itself outside every fence — a class a
dozen plan bodies have now named (ef0aed64, 2b19c560, a2d373e5 among them). If that
recurs much longer it is worth its own decision: whether the declaration's narration
is the operator's alone by design, or whether the file wants a phase that may write it.
