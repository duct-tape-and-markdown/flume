# The two prune siblings still route residue at prune alone

Shipped: `settleSlot`'s wall paragraph (`src/waveTick.ts`) now routes a
thrown wave's standing worktrees to the next `flume loop` start's sweep,
with prune named for what it does (metadata of a directory already gone),
and two pins on the narrowing in `tests/Dispatcher.test.ts`.

Observed, and left as declared per the entry: the two siblings the entry
named -- `src/waveTick.ts` at the `mergeError` throw and `src/waveMerge.ts`
in `commitPendingUpdate`'s header -- both read "the next `pruneWorktrees`
call reclaims their metadata once a human has cleared the refusal". True as
far as it goes, but each is the same operator-facing sentence as the one
just corrected, and neither names the sweep. If the human never deletes the
directories by hand, prune reclaims nothing and the sweep is the remover;
the two sentences read as if a human clearing the refusal is the only path.
Plan's call whether that is a third site of the same delta or a deliberate
narrowing to the human-repair case.

Fixture note for whoever next needs a wave that walls with a slot still
open: the ledger-rewrite refusal is the cheapest wall that fires *inside* a
slot before its settle -- the walling slot's own agent commits unreadable
bytes onto the queue, its span still lands on trunk, and the rewrite behind
it throws. So `verdict.shippedTags` names the walling entry too; a case
asserting only the settled entry shipped reads red for the wrong reason.
The refill read behind the settled slot meets the same bytes, but under the
default `**` fence it hands a parse failure back rather than throwing, so
which of the two set the wall does not change the outcome.
