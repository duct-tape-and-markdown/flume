# The band gate holds the filing half; a re-rank stays unread

`filing band` (`harness/gates.ts`) joins each plan slice's set: the engine's
queue listing at the commit against the same listing at `ctx.baseSha`, and
every *added* entry's `priority` against `harness/filingBands.ts`, which the
slice prompts now interpolate their numbers out of too.

**The spec's gate roster does not name it.** *The gates the discipline needs*
enumerates five and the merged-tree claim check; the band gate is a sixth, and
this entry's `per` is *The phases*, which is where the rule it holds lives.
Build cannot edit `spec/`, so that section and the shipped set now disagree by
one sentence — a human's to close.

Two things the next drain should know:

- A re-rank on a ruling is an amendment, so nothing checks it. That is the
  spec's shape (*The phases* rules re-ranking to the drain alone), but the
  enforced half is only the filing half — a drain that re-ranks to a band no
  slice files at reds nothing.
- The inbox row admits `30` and `20` only. A record whose real source is a
  spec commit cannot be filed by an inbox tick at `10`; it reds naming the
  tag. If that routing is real, it is a band-table question rather than a
  gate one.

`GateEngine` gained `parsePendingQueue` so the gate reads the engine's own
default for an omitted `priority` rather than copying `0` beside the schema.
The added files are parsed twice per plan commit as a result (pending gate over
the whole queue, this one over the added subset) — a handful of files, judged
cheap against a second spelling of a default.
